# Production-Architecture Causes of Test Cost

Four production structures materially shape test cost. Two have canonical findings; two are inherited context from the repository's own (deleted but git-preserved) performance audit, re-verified here.

1. **Per-operation unpooled connections under rollback-journal durability** — the ~58–60 ms floor beneath every store write, multiplied by every store-backed test and dominating the composition-root chain. Deliberately deferred decision (ORCH-3); possibly mooted by the event-sourced storage direction. → [findings/store-operation-durability-cost-no-wal-no-pooling.md](findings/store-operation-durability-cost-no-wal-no-pooling.md) (Measure first — the WAL comparison the prior audit already specified).
2. **Deep verification as the default storage-observation tier** — certification-strength whole-DB proof on routine local questions; prior audit's M3 already set the removal target. → [findings/deep-verification-default-on-routine-observations.md](findings/deep-verification-default-on-routine-observations.md) (Fix production ownership).
3. **Composition root performs immutable validation/hashing per construction** — catalog validation + SHA-256 over process-constant assets repeated ~90× per run by tests; unmeasured share. → [findings/composition-root-construction-repeated-per-test.md](findings/composition-root-construction-repeated-per-test.md) (Measure first).
4. **Test instrumentation living in production** — static counters + reset hook on `LoopRelayWorkspaceDatabase`; the price is a serialized test collection; retained because the measurement program consumes it. → [findings/test-counters-on-production-database.md](findings/test-counters-on-production-database.md) (Retain with explanation).

Re-verified inherited context (not new findings; strong prior evidence, unchanged source): `ProjectAsync`/`LoadSnapshotAsync` grow linearly with history (M2: 22.6×/47.3× across 100× history) — AR-3/PERF-05 read-scoping remains the production priority named by the prior audit; test histories are small, so test-side amplification today is minor. The `ReadTransitionEvidenceAsync` unbounded `SELECT document_json` (twice per kernel cycle) is the specific read. Any remediation here is production-roadmap work superseded-or-sequenced by the event-sourced direction; this audit only notes that its canaries (the keyed-read tests) are worth their cost — see [findings/perf-canary-seeding-through-production-stores.md](findings/perf-canary-seeding-through-production-stores.md) for making their setup proportionate.

Boundary of this audit: none of the above recommends distorting production architecture to accelerate tests. Items 1–2 are production defects/deferrals that tests merely amplify; item 3 is measurement-gated; item 4 is deliberately retained. The fifth historical item — full schema verify per store op (PERF-01) — was **already fixed** (stamp memo; warm ensure 0.95 ms) and is recorded here to prevent re-litigating it: the prior audit's own measurement redirected the leverage from PERF-01 to PERF-10.
